## Контекст

onlineTours — турагрегатор. У команды роста были гипотезы про SEO-лендинги и изменения UX воронки бронирования, но не было надёжного способа их протестировать. Существующий фронтенд представлял собой смесь legacy React и HTML, отрендеренного Rails, без библиотеки компонентов и без инфраструктуры A/B-тестирования.

## Что было построено

Два параллельных потока работ:

**1. Библиотека компонентов**
Библиотека компонентов на React + TypeScript со стилями на Tailwind и документацией в Storybook. Компоненты изначально проектировались с учётом A/B-тестов — каждый принимает проп `variant`, переключающий между контрольным и тестовым вариантом.

**2. Инфраструктура A/B-тестирования**
Серверное назначение экспериментальных флагов на Ruby on Rails. Пользователям детерминированно назначается вариант по хешу user ID — один и тот же пользователь всегда видит один и тот же вариант. Назначение хранится в Redis для быстрого чтения при каждой загрузке страницы.

## Выкаченные эксперименты

Самым результативным экспериментом стал редизайн **страницы списка туров** — конкретно отображения цены и сортировки по умолчанию. Тестовый вариант показывал цену сразу со всеми сборами (вместо базового паттерна «от X €»). Рост составил **11,63%** по основной метрике конверсии бронирования за 4-недельное окно.

## Технические заметки

**Почему Jotai для локального состояния?** Библиотеке компонентов было нужно лёгкое локальное состояние, не просачивающееся в глобальный Redux-стор. Модель атомов Jotai скоупится по дереву компонентов, что упрощает изоляцию состояния эксперимента.

**Почему серверное назначение?** Клиентское назначение A/B вызывает мерцание — пользователи на один кадр видят контрольную версию, прежде чем загрузится тестовый вариант. Серверное назначение означает, что нужный вариант уже есть в исходном HTML.

**Storybook как контракт.** У каждого компонента была story на каждый вариант, что ускоряло дизайн-ревью и сокращало циклы QA для новых экспериментов.

## Что бы я сделал иначе

Конфигурация экспериментов хранилась в кодовой базе Rails — изменение эксперимента требовало деплоя. Я бы вынес конфигурацию экспериментов в сервис фича-флагов (LaunchDarkly или простой JSON на Redis), чтобы продуктовая команда могла запускать и останавливать тесты без участия разработки.
