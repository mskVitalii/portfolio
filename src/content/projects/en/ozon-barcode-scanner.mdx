## The story, in brief

<StarStory>
<StarSituation>

OZON's returns zone ran on manual data entry, and the barcode scanners already on the floor were wired directly into a single legacy application — so retiring that app for a new interface would have meant buying a whole new batch of scanner hardware just to keep scanning working.

</StarSituation>
<StarTask>

Automate returns processing at the point of scan, and do it without locking the next interface migration — or any future one — to another hardware refresh.

</StarTask>
<StarAction>

Built a C# point-update service that scanners talk to over WebSockets, instead of wiring them into any one app directly. Terminals push scan events into a PostgreSQL-backed order pipeline through that shared service, so any app or interface can plug into the same backend — new terminals, and new UIs, scale out horizontally instead of each needing its own dedicated scanner integration.

</StarAction>
<StarResult>

€86,000/year saved in manual labour, the returns zone stopped being the workflow's bottleneck, and the next interface migration shipped without buying a single new scanner — the decoupling paid for itself again.

</StarResult>

## Context

The returns zone was OZON's slowest warehouse workflow — clerks manually logged every returned item into the order system by hand, which capped how fast a fulfilment centre could process returns as volume grew. The existing scanners were also wired directly into a single legacy app, which had made the previous interface migration expensive: retiring that app meant buying new scanner hardware for whatever replaced it. The goal was to automate at the point of scan, and stop tying scanner hardware to any one app in the process.

## What was built

- **C# service** integrating USB barcode scanner hardware at returns-zone terminals.
- **Real-time point-update service** pushing scan events over WebSockets into a PostgreSQL-backed order pipeline — a shared backend any app or interface can plug into, instead of scanners being wired to one app directly.
- Also rewrote a **Mattermost bot** that monitors warehouse errors, porting it from Python to C# for consistency with the rest of the stack.

## Architecture

```
  Terminal 2  ──USB──┼──►  C# Scanner Agent  ──WebSocket──►  Point-Update Service  ──►  PostgreSQL  ──►  Orders
  Terminal N  ──USB──┘                                              ▲
                                                                     │ targeted push
                                                          Central Config Service
                                                        (per-terminal agent/config
                                                         updates, no shared deploy)
```

## Technical decisions

**Why WebSockets over REST polling?** Scan events needed to land in the order system within milliseconds of a physical scan — polling would add latency and load for no benefit at this volume.

**Why route through a shared service instead of wiring scanners to the app?** The previous setup did exactly that, and it meant every app-level change risked a hardware refresh. A shared point-update service decouples the two: the app side can change or add new interfaces, and scale out with more terminals, without touching scanner integration at all.

**Why point-updates instead of a single deploy?** Terminals were spread across the returns-zone floor and couldn't all go offline at once during a rollout. A central config service pushed agent and config updates to each terminal individually, so a rollout never stalled the whole zone.

## Challenges

Coordinating updates across many independently-running terminal agents without a shared deploy window. A bad agent version at one terminal had to stay contained to that terminal's queue, not cascade into the rest of the zone.

## Observability

Reused the same Prometheus/Grafana stack as the warehouse search service. Per-terminal scan throughput and error rate were the key dashboards for catching a misbehaving terminal before it fell behind on returns.

## What I'd do differently

Add automated per-terminal health checks to the rollout pipeline itself, so a bad update surfaced immediately instead of waiting for a picker to notice a stuck queue.
